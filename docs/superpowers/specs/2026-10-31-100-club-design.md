# The 100 Club — consistency challenge (design, 2026-10-31)

## Intent

Every challenge so far asked "who can do the most" (longest plank, most situps, heaviest total).
The 100 Club asks "who keeps showing up": do 100 lifts this week, and if you do, the bar rises next
week. It runs on the existing challenge machinery (join, upload, analysis, leaderboard, champions)
so that nothing about uploading changes for the athlete.

Tom's decisions are marked **(Tom)**; everything else is the builder's call, already made here.

## Rules

- **Lifts that count (Tom):** Situp, Pushup, Squat, Plank. Situps, pushups and squats count one per
  rep. Situps keep the existing quality rule (clean reps in full, sloppy reps half:
  `attempt_rep_score`). Plank: every 10 s of hold is one lift (`floor(total_in_plank_s / 10)`).
  Any other lift type uploaded to the challenge counts zero.
- **Weeks (Tom):** Monday to Sunday. Week 1 starts Monday 2026-11-02. Eight weeks, so the last week
  ends Sunday 2026-12-27. The challenge timezone is `America/New_York` (this machine's zone); an
  upload belongs to the week of its `Attempt.created_at` converted to that zone. Uploads before
  2026-11-02 are warm-up: they appear on the athlete's history but score nothing.
- **Quota (Tom):** 100 in week 1. After a met week the next quota is 25 higher. After a missed week
  the next quota resets to 100. Nobody is eliminated.
- **Points (Tom):** per week, `min(lifts, quota)` + 50 if the quota was met + 25 for each type the
  athlete led that week (most situps, most pushups, most squats, most plank seconds; plank is judged
  on seconds, not on converted lifts).
- **Ranking (Tom):** total points, then current streak of met weeks, then weeks met, then this
  week's lifts, then name. Rows with zero points go last, like every other board.
- **Current week is live:** lift points and the quota bonus of the week in progress count toward the
  score as uploads land. Type bonuses count only for finished weeks; in the current week the leaders
  are shown as "leading" and lock when the week ends.
- **Ties for a type bonus:** everyone tied at the top gets it. An amount of zero never wins.
- **Pending analysis:** an attempt with no analysis result yet contributes zero lifts; the row
  carries `pending` (count of such attempts this week) so the UI can say "1 video still analysing".
- **Test accounts** (`User.is_test`) are excluded from the board, as on every other challenge.
- **Champion:** when the challenge ends, rank 1 with a truthy score becomes champion through the
  existing read-time `GET /champions` scan. The champion surfaces need to format a `consistency`
  score as points.

## Data model

No new table and no migration. The challenge is a `Competition` row whose description metadata
(JSON after ` - `) gains two keys next to `lifttypes`:

```json
{"lifttypes": ["Situp", "Pushup", "Squat", "Plank"], "weightclasses": [], "gender": "",
 "mode": "consistency",
 "rules": {"base_quota": 100, "ramp": 25, "weeks": 8, "quota_bonus": 50, "type_bonus": 25,
           "plank_seconds_per_lift": 10, "tz": "America/New_York", "week_start": "2026-11-02"}}
```

`POST /create_competition` must pass `mode` and `rules` through into that blob (today it hardcodes
the three legacy keys). `GET /competitions/<id>` returns `mode` and `rules` alongside `lifttypes`.
Missing `rules` keys fall back to the defaults above.

Everything (lifts per week, quotas, streaks, bonuses, points, rank) is computed on read from the
same participant/attempt rows `_leaderboard_payload` already loads. Late re-analysis self-corrects.

Prod row to create after deploy (via `POST /create_competition`, not SQL):

- name `The 100 Club`
- description text: `100 lifts a week. Situps, pushups, squats or planks. Hit it and the bar rises.`
- `start_date` = deploy time on 2026-10-31 (so the challenge is "ongoing" this weekend and people can
  join and warm up), `end_date` = `2026-12-27T23:59:59-05:00`, `status` = `in_progress` (what the
  other rows use; the frontend derives ongoing/upcoming/completed from the dates).
- `lifttypes`, `mode`, `rules` as above.

## API contract

`GET /competitions/<id>/leaderboard` keeps its shape and gains a fourth metric, `"consistency"`,
selected by `mode == "consistency"` **before** the lift-type inference (a mixed lift set would
otherwise fall through to `weight`).

```json
{
  "competition_id": "…", "metric": "consistency",
  "lift_types": ["Situp", "Pushup", "Squat", "Plank"],
  "momentum": {"joined": 4, "uploaded_today": 1},
  "consistency": {
    "rules": {…as stored, with defaults filled…},
    "status": "upcoming" | "live" | "ended",
    "week_index": 1,            // 1-based week in progress; 0 before week_start; weeks+1 after the end
    "weeks_total": 8,
    "week_start": "2026-11-02", "week_end": "2026-11-08",   // the week in progress (or week 1 / last week)
    "days_left": 3,             // whole days remaining in the week in progress, Sunday counts as 1; 0 outside
    "type_leaders": {"Situp": [{"user_id": "…", "name": "…", "amount": 60}], "Plank": [...] }
                                // week in progress, provisional; a list because of ties; omitted types have no leader
  },
  "rows": [{
    "rank": 1, "user_id": "…", "name": "…", "weight_class": null, "gender": null,
    "score": 325,               // total points
    "streak": 2, "best_streak": 2, "weeks_met": 2,
    "this_week": {"index": 3, "quota": 150, "lifts": 42, "met": false, "pending": 0,
                  "by_type": {"Situp": 30, "Pushup": 12, "Squat": 0, "Plank": 0},
                  "plank_seconds": 0, "leading": ["Situp"]},
    "weeks": [{"index": 1, "start": "2026-11-02", "quota": 100, "lifts": 112, "met": true,
               "points": 200, "bonuses": ["Situp", "Plank"], "by_type": {…}, "plank_seconds": 240,
               "pending": 0}, …],     // finished weeks and the week in progress, oldest first
    "warmup_lifts": 7,          // lifts uploaded before week_start (display only)
    "best_by_lift": {}, "form_score": null, "steadiness": null,
    "attempt_id": "…", "clip_url": "…", "thumbnail_url": null, "date": "2026-11-05",   // latest counted attempt
    "attempt_count": 7,
    "history": [{"score": 12, "date": "2026-11-03"}, …]   // lifts per counted attempt, chronological
  }]
}
```

`by_type` keys are the challenge's lift types. `this_week.index` is `week_index`; before the start
`this_week` describes week 1 with zero lifts; after the end it describes the last week.

## Backend

- `services/consistency.py` (pure, DB-free, mirrors `challenge_leaderboard.py`): `attempt_lifts`,
  `week_of`, `rank_consistency(participants, rules, now)` returning `(rows, consistency_block)`.
  `rank_challenge` dispatches `metric == "consistency"` to it (it needs `rules` and `now`, so give
  `rank_challenge` keyword args rather than a second entry point).
- `_leaderboard_payload`: parse `mode`/`rules` from the description, pick the metric, pass
  `now = datetime.now(timezone.utc)`. No new SQL columns are needed (`lift_type`, `status`,
  `created_at`, `held_s`, `reps`, `rep_form_scores` are already selected). If a column is added
  anyway, `_prow` in `tests/test_competition_routes.py` changes in the same commit.
- `get_competition_by_id` and `create_competition`: `mode` and `rules` round-trip.
- `GET /users/<id>/lifts` is untouched.
- **Admin preview `as_of`:** `GET /competitions/<id>/leaderboard?as_of=<ISO datetime>` computes the
  board as of that instant instead of now. It requires header `X-Admin-Token` matching `ADMIN_TOKEN`
  (same gate as tickets: 503 when unset, 401 on mismatch; without the param the route is public as
  before). `week_of` and the live-week logic key off `now`, so this is a one-line plumb, and it is
  what the production proof and Tom use to see week 1 scoring before Monday. The frontend never sends it.
- Squat uploads with weight `0` (air squats) must be accepted by the upload route; verify, do not assume.

Tests (all in `tools/run_ci_tests.sh`): `tests/test_consistency.py` covering week assignment at the
Sunday 23:30 local / Monday 03:30 UTC boundary, warm-up exclusion, the ramp and the reset, capped
lift points, quota bonus, type bonus with a tie and with a zero, plank exchange rate, situp
half-credit, the live current week with provisional leaders, pending attempts, `status` before /
during / after, and every ranking tiebreak. Route-level coverage in `test_competition_routes.py`
(metric selection by mode beats lift-type inference; legacy challenges unchanged) and a
`consistency` champion in `test_champions.py`. Every guard is mutation-checked: break the rule,
watch the test fail, restore.

## Frontend

- `ChallengeMetric` gains `"consistency"`; `ChallengeLeaderboard` gains the optional `consistency`
  block; `ChallengeLeaderboardRow` gains the optional `streak`, `weeks_met`, `this_week`, `weeks`,
  `warmup_lifts`. `Competition` gains optional `mode` and `rules` (parsed from the description
  metadata the same way `categories` is).
- `components/challenge/metric.ts`: `scoreColumnLabel` → `POINTS`, `scoreUnit` → `pts`,
  `formatScoreValue` → integer (or one decimal when a situp half-credit leaves a .5),
  `uploadCtaLabel` → `Log this week's lifts`, `scoringNote` → one line with the rules.
- `ChallengeDetail` on a consistency board, above the podium: `components/challenge/ConsistencyHero.tsx`
  (`data-testid="consistency-hero"`): "Week 3 of 8 · 3 days left" (or "Starts Monday 2 Nov" before
  the start, "Ended" after), the viewer's progress ring `42 / 150` with the streak flame, the
  "1 video still analysing" line when pending, and the type leader chips marked "leading". Anonymous
  visitors see the week line and the leaders, not the ring. Rows: `LeaderboardRow`/`YouRow`/`Podium`
  show points, a flame with the streak, and `42/150 this week`. The expandable per-athlete panel on a
  consistency board shows the week table (week, quota, lifts, met, bonuses, points) instead of the
  attempt list.
- Home to-do (`lib/prompts.ts` + `PromptList`): a consistency challenge is a `link` row whose pill
  reads `42 / 150 · 3 days left` (or `Starts Mon` before the start) when a `userId` is saved,
  fetched from the leaderboard payload (one request per consistency challenge, viewer row by
  `userId`); anonymous visitors get the plain link row. It links to `/challenges/<id>`, never the
  bare upload route (multi-category rule).
- Champions: `TrophyCase.championTitle`, `ChampionSpotlight` and `HallOfChampions` format a
  `consistency` score as `325 pts`.
- Upload flow: the challenge upload page must list exactly the four lift types, hide weight for the
  bodyweight three and allow `0` for Squat. Verify in the browser; `ChallengeDetail` has a scope bug
  history that tsc does not catch.
- Phone and desktop split by width as everywhere else; check both at 390 px and desktop.

Tests: `metric.test.ts`, `ConsistencyHero.test.tsx`, `prompts.test.ts` (pill text, anonymous), a
`ChallengeDetail` render with a consistency fixture (hero + rows + week table), champions formatting.
`jest.setup.js` stubs `localStorage` with `jest.fn()` (mock `getItem`); page tests mock `../../config`.

## Non-goals

- No notification or reminder emails. No new table. No admin UI for `mode`/`rules` (created via API).
- No changes to how other challenges rank. No engine changes; squat rep counting uses the engine as
  deployed (`EXERCISE_CONFIGS["squat"]`, never validated on real footage in this app, stated as a
  limitation in the reference doc).
- No elimination mechanic.

## Verification in production

Backend deploy (`python3 deploy.py --backend-only --skip-iam`) then frontend
(`--frontend-only --skip-iam`). Create the challenge through the API. Then, in the browser at the prod
URL (wait ~1 s after the first navigation for the stale-chunk reload): challenges page lists The 100
Club as open; the detail page shows the hero in its pre-start state with the rules line; a throwaway
non-test user joins and uploads `backend/tests/fixtures/test_video_plank_10s.mp4`, the analysis
completes, and the row shows a warm-up lift and zero points. Then seed one attempt row dated inside
week 1 for the same throwaway user by SQL (Cloud SQL proxy, `db-password` secret), confirm the API
and the page count it (plank seconds / 10, quota 100 shown, points = lifts), and delete the throwaway
data in the documented order (AnalysisNotification → ShortLink → LiftingResult → Attempt →
UserCompetition → User, plus the GCS objects). Every claim states what was run and what it did not
cover.
